# DocumentSummarizer

## 问题陈述

我们如何为 tRPC-Agent-Go 构建一个纯本地、零 LLM 依赖的 Markdown 文档结构解析器，能够对流式输入进行首次解析并缓存结构结果，输出线性 `[]Region` 列表供下游 RAG 链路和大模型通过位置引用快速定位内容，从而消除全量 LLM 读取的高 Token 开销？

## 推荐方向

**流式两阶段解析器 + YAML 旁路缓存 + Region 内容检索器**。核心选择：

1. **解析方式**：采用 `Goldmark`（Go 标准 Markdown 库）构建 AST，支持标准 Markdown 和 GFM 扩展
2. **流式设计**：虽然底层仍需读入全文做 AST 解析，但通过 `io.Reader` 接口和行号预计算支持大文件分块处理
3. **缓存策略**：旁路缓存文件 `filename.md.summary.yaml`，首次解析后写入，后续直接读取
4. **Region 模型**：线性 `[]Region` 列表，每个 Region 标注类型 + 位置（起始行/结束行）+ 内容预览（前200字符）+ 元数据
5. **内容检索**：提供 `RegionContentReader`，通过 Region 的 StartLine/EndLine 从原始文件快速定位并提取内容

### 与现有代码库的集成

- 包路径：`trpc.group/trpc-go/trpc-agent-go/knowledge/summarizer/`
- 复用模式：遵循 Reader Registry 的 `Option` 函数式配置风格
- 注册机制：可选的 `Summarizer.GetReader()` 方法可与现有 Reader 管线串联

## 关键设计决策

### Region 类型定义

```go
type RegionType int

const (
    RegionFrontMatter  RegionType = iota // YAML/TOML 前置元数据
    RegionHeading                         // # ~ ###### 标题
    RegionParagraph                       // 普通段落
    RegionCodeBlock                       // ``` 代码块
    RegionTable                           // | 表格
    RegionList                            // - / 1. 列表
    RegionHTML                            // <tag> 原始 HTML
    RegionBlockquote                      // > 引用
    RegionHorizontalRule                  // --- 分隔线
    RegionMathBlock                       // $$ 数学公式
    RegionDefinitionList                  // 定义列表
)
```

### Region 结构

```go
type Region struct {
    Type      RegionType         `yaml:"type"`
    StartLine int                `yaml:"start_line"`
    EndLine   int                `yaml:"end_line"`
    Preview   string             `yaml:"preview"`       // 前 200 字符
    Level     int                `yaml:"level,omitempty"` // 标题级别
    Heading   string             `yaml:"heading,omitempty"`
    Language  string             `yaml:"language,omitempty"` // 代码语言
    Metadata  map[string]any     `yaml:"metadata,omitempty"`
}
```

### 核心接口

```go
// DocumentSummarizer 文档结构解析器的主接口
type DocumentSummarizer interface {
    // Summarize 解析文档并返回区域列表
    Summarize(ctx context.Context, path string) ([]*Region, error)

    // SummarizeFromReader 从 io.Reader 解析内容
    SummarizeFromReader(ctx context.Context, name string, r io.Reader) ([]*Region, error)

    // SupportedExtensions 返回支持的文件扩展名
    SupportedExtensions() []string
}

// ContentRetriever 基于 Region 从原文件检索完整内容
type ContentRetriever interface {
    // GetContent 根据 Region 从文件读取对应的完整原文
    GetContent(path string, region *Region) (string, error)

    // GetContentByRange 按行范围读取文件
    GetContentByRange(path string, startLine, endLine int) (string, error)
}
```

### 解析流程

```
文件路径
    │
    ├─→ 检查缓存文件 .md.summary.yaml 是否存在
    │   ├─ 是 → 反序列化 YAML → 返回 []*Region（零解析）
    │   └─ 否 → 继续
    │
    ├─→ Step 1: Preprocessor（修复阶段）
    │   ├─ 修复不闭合的代码栅栏
    │   ├─ 修复表格列不对齐
    │   ├─ 修复 HTML 标签不闭合
    │   └─ 混合换行符统一
    │
    ├─→ Step 2: AST Parser（解析阶段）
    │   ├─ Goldmark AST 遍历
    │   ├─ 行号映射（通过源码位置映射）
    │   └─ 生成 []*Region（含 Preview + Metadata）
    │
    ├─→ Step 3: Cache Writer（缓存写出）
    │   ├─ 序列化为 YAML
    │   └─ 写入 .md.summary.yaml
    │
    └─→ 返回 []*Region
```

### 缓存机制

| 属性 | 策略 |
|------|------|
| 缓存文件名 | `{original}.md.summary.yaml` |
| 存储位置 | 与原始文件同目录 |
| 失效策略 | 通过文件修改时间 (`mtime`) 检测，源文件更新则重解析 |
| 格式 | YAML（用户指定） |
| 文件头 | 包含 `# generated by agent-go summarizer v0.1` + `# source_mtime: 2026-05-27T...` |

### 内容检索机制

```go
// 大模型或其他工具的使用方式
retriever := summarizer.NewContentRetriever()

// 1. 先解析得到 Region 列表
regions, _ := summarizer.Summarize(ctx, "doc.md")

// 2. 按类型过滤
for _, r := range regions {
    if r.Type == RegionTable {
        // 3. 通过 Retriever 获取完整内容
        fullContent, _ := retriever.GetContent("doc.md", r)
        // fullContent 包含整个表格的完整原文
    }
    if r.Type == RegionCodeBlock && r.Language == "go" {
        code, _ := retriever.GetContent("doc.md", r)
        // 提取特定 Go 代码块
    }
}
```

## 需要验证的关键假设

- [ ] **Goldmark 对残缺 Markdown 的容错能力**：OCR/PDF 转换的 MD 可能包含 `goldmark` 无法解析的语法，需要评估是否需要 fallback 到纯正则解析器
- [ ] **行号定位的准确性**：预处理阶段的行号变化需与最终 Region 行号对齐，否则 `ContentRetriever` 会定位到错误位置
- [ ] **YAML 缓存体积**：大文档（10MB+）的 Region 列表序列化为 YAML 后是否过大，是否需要考虑分片
- [ ] **Mtime 比较的跨平台一致性**：不同文件系统（NTFS/ext4）的 mtime 精度差异是否会导致缓存误命中

## MVP 范围

### 包含

- `Region` 类型系统（10 种基础类型）
- `DocumentSummarizer` 主接口 + `Goldmark` 解析实现
- `Preprocessor`（修复常见 3 类转换问题：代码栅栏、表格、HTML 闭合）
- `ContentRetriever`（基于行范围的文件读取）
- YAML 缓存读写 + mtime 校验
- 单元测试覆盖：标准 Markdown、残缺 Markdown、含表格/代码块/HTML 混合文档
- 与现有知识库管线集成（提供 `summarizer.New()` 函数）

### 不包含

| 事项 | 原因 |
|------|------|
| 非 Markdown 格式的直接解析 | 用户指定输入范围仅为 `.md` |
| LLM 辅助的语义级摘要 | 用户指定纯本地解析 |
| 缓存压缩或分片 | MVP 阶段无需优化极限场景 |
| 文件热更新监控（inotify） | 超出 MVP 范围，mtime 检查已足够 |
| 流式分块内存管理 | MVP 先用 `io.ReadAll`，后续可根据需要优化 |
| Front Matter 结构化提取 | 仅识别为 Region，不做 schema 级别的解析 |

## 未解决问题

1. **Goldmark 备用方案**：如果 Goldmark 对残缺 Markdown 解析失败率过高，是否需要内置一个正则 fallback 解析器作为兜底？
2. **Region Preview 长度策略**：200 字符是硬限制还是可配置？对于表格，Preview 应该包含表头行还是内容的前 N 行？
3. **缓存安全**：是否存在缓存投毒的风险（恶意构造 `.md.summary.yaml` 文件）？是否需要对缓存内容做校验和？
4. **并发安全**：多个 Agent 实例同时解析同一文件时，缓存写入是否需要文件锁？
